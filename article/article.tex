\begin{abstract}
哈希表是支持动态数据操作的基础数据结构，其时空权衡一直是算法研究的核心议题。
2021年，Bender等人提出了一种基于$k$-kick树的新型哈希方案，从理论上证明
可通过将更新操作的时间复杂度放宽至$O(k)$，将每元素的空间浪费指数级压缩至
$O(\log^{(k)} n)$比特，打破了此前$\Omega(\log\log n)$的空间下界。
本文复现了该哈希算法，构建了分层弹性哈希存储结构（Facility与Cubby），实现了
论文§3.1的优先级踢出机制，并将§4.3的局部查询路由器重构为二叉Trie最小唯一前缀
结构（论文Lemma 15），通过MiniArray位压缩数组将槽元数据压缩至每槽4比特。
在$n\leq 2^{20}$个32位键值对的实验规模下，与\texttt{std::unordered\_map}和
\texttt{std::map}进行了插入、查询、删除及空间占用的全面对比。实验表明，插入瓶颈
来自合并时的全量路由重建（$n=5\times10^5$处陡升至37.6 s），查询3.11 s
（vs map 1.69 s，受全局路由器规模及Trie对象式节点影响），空间占用211 MB
（Trie节点32B/个 vs 论文紧凑编码 ∼2.5 bytes/key）。分析表明论文的per-cubby
独立路由架构和紧凑编码E$_1$+E$_2$是实现理论空间界的关键。
最后将方案集成为LevelDB MemTable的点查询加速器，提供
\texttt{-DUSE\_KICK\_HASH}编译期开关。

\noindent\textbf{关键词}：哈希表，时空权衡，k-kick树，弹性哈希，位压缩路由，LevelDB
\end{abstract}

\begin{abstract*}
Hash tables are fundamental data structures supporting dynamic data operations,
with their time-space tradeoffs being a core topic in algorithm research.
In 2021, Bender et al.\ proposed a novel hashing scheme based on $k$-kick trees,
theoretically proving that by relaxing update time to $O(k)$, per-element space
waste can be exponentially compressed to $O(\log^{(k)} n)$ bits, breaking the
previous $\Omega(\log\log n)$ lower bound. This thesis implements the algorithm,
constructing a hierarchical elastic hash storage structure (Facility and Cubby),
implementing the priority-based kicking mechanism (§3.1) and refactoring the
local query router (§4.3) into a binary trie of smallest unique prefixes
(Lemma 15), with slot metadata compressed to 4 bits via MiniArray bit-packing.
Experiments with $n\leq 2^{20}$ 32-bit key-value pairs compare insertion, query,
deletion and space against \texttt{std::unordered\_map} and \texttt{std::map}.
The insertion bottleneck stems from full route-table rebuilds during merges
(spike to 37.6 s at $n=5\times10^5$), query takes 3.11 s (vs map 1.69 s,
affected by global router scale and object-oriented trie nodes), and memory is
211 MB (TrieNode 32B/node vs paper's compact encoding $\sim$2.5 bytes/key).
Analysis reveals that the paper's per-cubby independent routing architecture
and compact encoding E$_1$+E$_2$ are essential for achieving theoretical space bounds.
The scheme is integrated into LevelDB's MemTable with a \texttt{-DUSE\_KICK\_HASH}
compile-time switch.

\noindent\textbf{Keywords}: hash table, time-space tradeoff, k-kick tree, elastic hashing, bit-packed routing, LevelDB
\end{abstract*}

\section{研究背景和意义}

哈希表是现代数据库管理系统、缓存系统和搜索引擎中最为基础的数据结构之一。
其核心目标是支持动态插入和删除操作，并保证查询的时间复杂度为$O(1)$，
即在理想状态下，查询、插入、删除的操作所需时间为常数级，不随存储数据量
$n$的增大而增加。为了实现这一点，哈希表往往需要在空间占用上做出让步，
通过额外的比特位存储信息来实现极低的时间复杂度。

在要求插入、删除及查询操作均维持恒定时间复杂度（即期望时间或最坏情况时间为
$O(1)$）的前提下，早期的理论工作\cite{pagh2001low}表明，在严格限制更新操作
为$O(1)$时间且仅使用简单探测序列的模型下，每个键值对的空间冗余往往难以低于
$\Omega(\log \log n)$比特。这一理论下界长期制约着哈希表空间效率的进一步提升。

2021年，Bender等人发表的论文《关于哈希表最优时间/空间权衡》%
\cite{bender2022optimal}打破了这一僵局。这项研究提出了一种基于$k$-kick树
的新哈希方案，证明通过适当提高插入和删除操作的时间复杂度（从$O(1)$提高到
$O(k)$，其中$k$是一个人为指定的具有一定上限的常数），空间浪费可以以指数形式
降低至$O(\log^{(k)} n)$比特。这里$\log^{(k)} n$表示对$n$进行$k$次迭代对数
运算，即$\log^{(k)} n = \log(\log^{(k-1)} n)$，并定义$\log^{(0)} n = n$、
$\log^{(1)} n = \log n$。当$k = \log^{*} n$（等式右侧表示对$n$进行迭代求对数
直到结果小于等于1所需的次数，此时$\log^{(k)} n = O(1)$）时，空间浪费可以降低
到恒定的$O(1)$比特水平，实现了理论和工程上的重大突破。

本毕业设计旨在复现这一前沿的哈希算法，并将其集成到常见的数据库管理系统中。
研究意义如下：

\textbf{理论价值}：通过实验对论文理论进行验证，通过调整$k$的值研究$k$如何
影响时间与空间复杂度，探索最优的$k$值选择策略。

\textbf{工程价值}：减少内存使用意味着成本降低和并发能力增强，在内存有限
的场景中提高现有数据库的存储效率。将其集成到数据库观察空间存储效率提升
效果。

\section{研究现状}

哈希表作为支持几乎常数时间的插入、删除和查询操作的核心数据结构，其时间复杂度
和空间复杂度之间的权衡一直是现代算法的研究焦点。

\subsection{链式寻址法}

链式寻址法通过链表处理冲突和碰撞的问题，它在实现上相对简单并且支持动态扩容，
但每个节点都需要存储额外的指针开销，在查询时的探测深度也相当不平衡。链表节点
在内存中的非连续分布还会破坏缓存局部性，导致更高概率的缓存缺失。

\subsection{开放寻址法}

开放寻址法（如线性探测、二次探测）将所有元素存储于连续数组中，通过一个固定的
探测序列函数处理冲突。当当前元素哈希结果与已存入的元素冲突时，沿着探测序列
寻找下一个位置，直到不发生冲突。然而，随着负载因子$\alpha$趋近于1，冲突链
长度急剧增加，导致查询与插入因为要沿着长长的探测序列进行操作，时间复杂度退化。
因此其难以在保证$O(1)$时间复杂度的同时维持极高的空间利用率。

\subsection{Cuckoo Hashing}

Cuckoo Hashing由Pagh和Rodler于2001年提出\cite{pagh2004cuckoo}，通过引入
多候选位置及元素重定位机制，在最坏情况下实现了$O(1)$的查询时间。多候选位置
改变了先前使用一个关于探测次数的探测函数生成探测序列的方式，转而采用多个哈希
函数为每个元素生成多个可存入位置，每一个元素只会出现在属于自己的可存入位置中。
元素重定位机制则从发现冲突退让并探测转变为发现可存入位置都有冲突就踢出一个
元素，将该元素往属于它的其他可存入位置移动，重复进行直到不再冲突。这两种机制
协作严格保证了任何键的查找操作只需要计算预先设置的哈希函数个数的次数，实现了
常数级查询。

\subsection{基于k-kick树的时空最优方案}

上述所有解决方案均未能突破前面提出的空间限制下界。而2021年发表的论文《关于
哈希表时间/空间权衡的最优方案》\cite{bender2022optimal}中提出的利用$k$-kick
树结构构建哈希表方案是目前最新的突破成果。该方案将哈希表映射问题转化为一个
层次化的``球到槽''问题，通过引入随机优先级和有限的不超过人为确定的$k$次元素
移动（即``$k$-kick''），从理论上证明，对于任何$k \geq 1$，都可以实现$O(k)$
时间复杂度的哈希表元素更新（插入、删除、查询）和$O(\log^{(k)} n)$比特的空间
浪费。

该研究还证明了此权衡曲线对于所有基于``增强开放寻址''框架的哈希表是紧确的
\cite{bender2022optimal}，即任何此类方案若更新时间为$t$，则每元素必须使用
$\Omega(\log^{(t)} n)$位的冗余。这意味着，若要在次对数级的更新时间下实现
$O(1)$位的空间冗余，必须彻底脱离``增强开放寻址''的范式。

\section{主要研究内容和目标}

本选题旨在复现并验证2021年提出的基于$k$-kick树的最优时空权衡哈希算法，
并探索其在数据库存储中的实际应用潜力。具体研究内容包括以下四个目标：

\begin{enumerate}
  \item \textbf{数据结构的实现和算法复现}：依照论文中的定义，构建基于$k$-kick树
    的分层存储结构，并实现从根节点到叶节点的动态元素分配逻辑。实现高效的kick
    策略，模拟论文中的随机优先级机制，建立在插入冲突时通过$k$次元素移动将
    新元素安置或触发上层重组并完成的机制，保证$O(k)$的时间复杂度。实现紧凑
    的辅助路由结构，用于快速定位元素所在的探测层级。

  \item \textbf{数据库存储集成与适配}：设计形式化的哈希表操作接口，对外只暴露
    insert、delete、get等操作，屏蔽底层逻辑设计提高兼容性。

  \item \textbf{理论正确性验证与复杂度分析}：基于代码实现，形式化验证算法
    复杂度，结合理论推导与实验数据，量化分析参数$k$对更新时间$T(n)$和空间
    浪费$S(n)$的具体影响，验证$S(n) = O(\log^{(k)} n)$的正确性。

  \item \textbf{性能对比实验}：构建包含标准库中的\texttt{std::unordered\_map}和
    \texttt{std::map}作为对照组，在相同硬件环境下进行全方位性能比对。测试不同
    数据规模下插入、查询、删除操作的时间开销和空间占用情况。
\end{enumerate}

\chapter{相关理论基础}

\section{哈希表基本概念}

哈希表（Hash Table）是一种通过哈希函数将键（key）映射到表中位置（slot）
来实现快速数据存取的数据结构。一个标准的哈希表支持三种基本操作：

\begin{itemize}
  \item \textbf{插入}（Insert）：将键值对$(k, v)$存入表中
  \item \textbf{查询}（Query/Lookup）：给定键$k$，返回对应的值$v$
  \item \textbf{删除}（Delete）：给定键$k$，从表中移除对应记录
\end{itemize}

理想情况下，三种操作均可在$O(1)$时间内完成。然而，当两个不同的键被哈希函数
映射到同一位置时，就会发生\textbf{冲突}（collision）。冲突处理策略是哈希表设计
的核心难题，不同的策略直接决定了哈希表在时间效率和空间占用上的表现。

\subsection{哈希函数}

哈希函数$h: U \rightarrow [m]$将键从全域$U$映射到$m$个槽中。一个好的哈希函数
应满足：
\begin{itemize}
  \item \textbf{确定性}：同一键总是映射到同一位置
  \item \textbf{均匀性}：每个槽被映射到的概率近似相等
  \item \textbf{高效性}：计算速度快，$O(1)$时间
\end{itemize}

本文使用\texttt{splitmix64}\cite{stafford2007splitmix}作为最终化函数，对不同的
使用场景通过不同种子值（seed）生成独立哈希族\cite{belazzougui2009hash}。

\subsection{负载因子与空间效率}

负载因子（load factor）$\alpha = n/m$表示当前存储元素数$n$与总槽数$m$的比值。
空间效率通常用\textbf{每键浪费比特数}（wasted bits per key）$r$来衡量：
若信息论最优空间为$\mathcal{B}$比特，哈希表使用$\mathcal{B} + rn$比特，则称
浪费了$r$比特/键。本文研究的核心问题是如何在保障时间效率的前提下最小化$r$。

\section{Cuckoo Hashing}

Cuckoo Hashing\cite{pagh2004cuckoo}是一种经典的开地址哈希方案，其核心思想
是每个键有$d$个候选位置（通常$d=2$），由$d$个独立哈希函数分别确定。
当插入新键时：
\begin{enumerate}
  \item 依次检查$d$个候选位置，找到第一个空位即插入
  \item 若所有候选位置均被占用，随机选择一个候选位置上的现有键``踢出''（kick out），
    新键占据该位置
  \item 被踢出的键尝试在其\textbf{其他}候选位置中寻找空位
  \item 重复上述过程，直到所有键都找到位置或达到预设的最大踢出次数
\end{enumerate}

Cuckoo Hashing的优势在于\textbf{查询严格为$O(1)$}（只需检查$d$个位置），
但其负载因子通常受限（$d=2$时约$50\%$）。

\section{k-kick树哈希方案}

Bender等人\cite{bender2022optimal}提出的$k$-kick树方案是对Cuckoo思路的重大
推广。其核心创新在于：

\subsection{多层级bin划分}

将哈希表的$m$个槽组织为$k+1$个层级（depth $0,1,\ldots,k$）的bin层次结构。
Depth-0的bin包含全部$m$个槽，depth-$i$（$i>0$）的bin大小为
$s_i = \Theta((\log^{(i)} m)^6)$。随着深度增加，bin大小呈指数级递减。
这种层次结构被称为\textbf{$k$-kick树}。

\subsection{优先级踢出策略}

每个键$x$被随机分配一个最大深度$s(x)$，满足
$\Pr[s(x) < i] = 1/(\log^{(i)} n)^2$。插入时按以下规则操作：

\begin{enumerate}
  \item 新键$x$试图在尽可能深的bin中寻找空位
  \item 若目标bin无空位且\textbf{未饱和}（存在深度较低的键）：
    踢出该低深度键，新键占据其位置
  \item 被踢键\textbf{保持原深度不变}，在其自身深度bin中寻找新空位
  \item 被踢键若触发新一轮踢出，则形成\textbf{踢出链}，但总踢出次数不超过$k$
\end{enumerate}

\textbf{关键性质}：高深度（小bin）的键优先踢出低深度（大bin）的键，被踢键
保持原深度。每次插入至多触发$k$次踢出，因此\textbf{切换开销}为$O(k)$。

\subsection{理论保证}

论文证明，对于任意$k \in [\log^* n]$，上述方案可实现：
\begin{itemize}
  \item 插入/删除时间：$O(k)$（高概率）
  \item 查询时间：$O(1)$（确定性）
  \item 每键空间浪费：$O(\log^{(k)} n)$比特（高概率）
\end{itemize}

此结果打破了长期存在的$\Omega(\log\log n)$空间下界，展示了时空权衡的极致
曲线：每次增加常数的更新时间，空间浪费可\textbf{指数级减少}。

\chapter{系统设计}

本章描述基于$k$-kick树的哈希方案的系统设计。系统由四层组件构成：
\texttt{MiniArray}（位压缩数组原语）、\texttt{LocalQueryRouter}（局部查询路由）、
\texttt{Cubby}（单级弹性哈希表）和\texttt{Facility}（全局分层管理器）。

\section{MiniArray：位压缩数组}

\subsection{设计动机}

在紧凑哈希表中，大量元数据（槽状态、路由条目）的位宽远小于标准整型（64 bits）。
例如槽元数据仅需4比特（occupied + depth），路由条目中cubby索引仅需11比特。
若使用\texttt{std::vector<uint64\_t>}存储，每个元素固定64比特，造成严重空间浪费。

MiniArray通过将元素紧密平铺在连续位流中，实现了\textbf{精确位宽存储}。

\subsection{双模存储}

\end{figure}

\begin{itemize}
  \item \textbf{Uniform模式}：所有元素位宽$w$相等，第$i$个元素位于\texttt{data\_}的
    位偏移$i \times w$处，通过\texttt{bit\_read}/\texttt{bit\_write}直接存取
  \item \textbf{Non-uniform模式}：元素位宽不等时启用，使用\texttt{lens\_[]}和
    \texttt{vals\_[]}分别存储每个元素的位长和值；修改操作后调用
    \texttt{rebuild\_uniform()}尝试切回Uniform模式
\end{itemize}

\section{LocalQueryRouter：二叉Trie局部查询路由}

\subsection{设计原理（论文 §4.3 + Lemma 15）}

论文的局部查询路由器将每个键$x$哈希为64-bit全随机二元串$r_x$，在集合$S$上构建
\textbf{最小唯一前缀二叉Trie} $T$：对每个$r_x$，取最短的、不与任何其他$r_y$冲突
的前缀作为该键的唯一标识。Trie 的叶节点存储该键对应的 probe 值 $f(x)$。

论文 Lemma 15 证明：随机二元串的 Trie 期望规模为 $O(k)$ 个节点（其中 $k=|S|$），
且对任意常数 $c>1$，存在 $\varepsilon>0$ 使得 $|T|\leq (\log n)/c$ 以高概率成立。

\subsection{紧凑编码方案（论文，本次未实现）}

论文将 Trie 及 f-values 编码为两部分：
\begin{itemize}
  \item \textbf{E$_1$（树结构）}：DFS 遍历指令流（go-left=10, go-right=11, go-up=0），
    $\sim 2$ bits/edge，高概率 $\leq (\log n)/c$ bits
  \item \textbf{E$_2$（f-values）}：按 DFS 叶出现顺序排列 f-values，自定界编码
\end{itemize}
整体空间 $= |E_1|+|E_2| = O(|S|+\sum_{s\in S}\log f(s))$ bits，通过 lookup table
（Method of Four Russians）实现所有操作 $O(1)$ 时间。

\subsection{本次实现的 Trie 结构}

本次实现使用内存对象式 Trie（\texttt{vector<TrieNode>}）替代紧凑编码：

\begin{figure}[H]
\centering
\begin{verbatim}
TrieNode {
    child[0], child[1]   ← 子节点索引 (-1=空)
    parent               ← 父节点索引 (删除回溯)
    f_value              ← probe值 (叶节点有效)
    key_hash_val         ← 键哈希指纹 (无oracle时验证)
    is_leaf              ← 最小唯一前缀终点标志
}
\end{verbatim}
\caption{TrieNode 节点结构}
\label{fig:trienode}
\end{figure}

\textbf{核心操作}：
\begin{itemize}
  \item \textbf{Query}：沿键的哈希位遍历 Trie，遇叶节点用 oracle/指纹验证后返回 f\_value
  \item \textbf{Insert}：沿路径 walk → 遇异键叶节点时\texttt{split\_node()}分裂
    （找两键哈希分叉位 → 创建内部节点链 → 创建两叶）→ 路径断时创建新叶
  \item \textbf{Delete}：find leaf → \texttt{cleanup\_leaf()}沿 parent 回溯删除单子内部节点链
\end{itemize}

\textbf{键验证}：当 oracle 函数 $g=f^{-1}$ 存在时，通过 g(f\_value) 还原键后比较；
无 oracle 时存储完整 64-bit \texttt{key\_hash\_val} 作为指纹进行匹配。

\section{Cubby：单级弹性哈希表}

Cubby是$k$-kick树的载体。每个Cubby有固定容量$m$（由tier决定）和$k+1$个深度层级。

\subsection{槽元数据编码}

每槽使用4比特位压缩存储：
\begin{itemize}
  \item bit 0: occupied（1=已占用）
  \item bit 1--3: depth（0--7，该槽所在kick深度）
\end{itemize}

\subsection{踢出算法}

Cubby的核心算法\texttt{try\_place}实现了论文§3.1的优先级踢出：

\begin{algorithm}[H]
\caption{try\_place(key, max\_depth)}
\begin{algorithmic}[1]
\FOR{$d = max\_depth$ down to $0$}
  \STATE $bin \gets bin\_for\_key(key, d)$
  \STATE Phase 1: 扫描$bin$，若找到空槽则返回
  \IF{$d > 0$}
    \STATE Phase 2: 扫描$bin$中深度$< d$的占槽
    \IF{找到}
      \STATE 暂存$victim\_key, victim\_val$
      \STATE 清空该槽
      \STATE 递归\texttt{try\_place}(victim, victim\_depth, kick\_idx)
      \IF{成功}
        \STATE victim移入新槽，新键占据该槽
        \RETURN
      \ELSE
        \STATE 恢复原槽
      \ENDIF
    \ENDIF
  \ENDIF
\ENDFOR
\RETURN FAIL
\end{algorithmic}
\end{algorithm}

被踢键\textbf{保持原深度}，在其自身深度bin中寻找新空位。算法中的\texttt{reserved}
参数防止被踢键在递归扫描时``发现''刚被清空的原槽，避免了数据丢失的bug。

\section{LocalQueryRouter实现（二叉Trie）}

\subsection{TrieNode 结构}

\begin{figure}[H]
\centering
\begin{verbatim}
struct TrieNode {
    int32_t child[2];     // 左右子节点索引 (-1=无)
    int32_t parent;       // 父节点索引 (删除时 O(1) 回溯)
    uint64_t f_value;     // probe 值 (叶节点有效)
    uint64_t key_hash_val;// 键哈希指纹 (无 oracle 时验证)
    bool is_leaf;         // 最小唯一前缀终点标志
};  // 共 32 bytes
\end{verbatim}
\caption{TrieNode 节点结构（32 bytes）}
\label{fig:trienode_impl}
\end{figure}

\subsection{核心算法}

\textbf{查询 (probe\_index)}：对 key 计算 \texttt{splitmix64(hash)} 得到 64-bit 二元串，
从根节点沿位遍历 Trie。每遇 \texttt{is\_leaf} 节点即用 oracle 或 \texttt{key\_hash\_val}
指纹验证是否为当前键；若是则返回 \texttt{f\_value}，否则继续向下遍历。
若路径中断（无对应方向的子节点），返回 SIZE\_MAX。

\textbf{插入 (insert)}：沿 key 的 hash 位遍历 Trie。三种情况：
\begin{enumerate}
  \item 遇叶节点且指纹匹配 → 更新 \texttt{f\_value}，返回
  \item 遇叶节点但指纹不匹配 → 调用 \texttt{split\_node()} 分裂：
    找两键 hash 的分叉深度 $d'$ → 创建 $d'-d$ 个内部节点链 → 在分叉处创建两叶节点
  \item 路径中断 → 创建新叶节点，链接到当前父节点，存储 \texttt{f\_value} 和哈希指纹
\end{enumerate}

\textbf{split\_node(node\_idx, ehash, nhash, nfval, start\_depth)}：
\begin{enumerate}
  \item 保存原叶节点的 \texttt{f\_value} 和 \texttt{key\_hash\_val}
  \item 将原叶节点转换为内部节点（\texttt{is\_leaf=false}）
  \item 找两 hash 在 start\_depth 后的第一个分叉位 diverge
  \item 从 start\_depth 到 diverge-1 逐位创建内部节点链
  \item 在 diverge 处创建两叶：e\_leaf（原键，保存的旧值）和 n\_leaf（新键，nfval）
  \item 所有新节点正确设置 parent 指针
\end{enumerate}

\textbf{删除 (remove)}：沿 Trie walk 找到匹配叶节点 → 调用 \texttt{cleanup\_leaf()}：
标记 \texttt{is\_leaf=false}，若该节点无子节点则沿 parent 回溯删除整条单子内部节点链。

\textbf{键验证}：当 \texttt{oracle\_}（论文的 $g=f^{-1}$ 函数）存在时，通过 $g(f\_value)$
还原键并比较；无 oracle 时存储完整 64-bit \texttt{key\_hash\_val} 作为指纹，查询时重算 hash 比较。

\subsection{与论文编码的差异}

论文 §4.3 将 Trie 紧凑编码为 E$_1$（DFS 遍历指令：go-left=10, go-right=11, go-up=0, $\sim$2 bits/edge）
+ E$_2$（叶 f-values 序列），并通过 lookup table 实现 $O(1)$ 操作。本次实现使用
内存对象式 \texttt{vector<TrieNode>}（32B/节点）替代，空间约 $\sim$150× 论文，
但正确实现了 Trie 的语义和所有操作（query/insert/split/delete）。

\section{Cubby实现}

\subsection{bin参数计算}

\texttt{compute\_kick\_params()}：从\texttt{capacity\_}出发迭代
$\lceil\log_2(x+1)\rceil$得到$k$（$\le 4$），对每层应用4次$\log_2$压缩后平方取整
得到\texttt{s\_[i]}。初始化\texttt{free\_count\_[d]}为各深度的总槽数。

\subsection{深度分配}

\texttt{max\_depth\_for(key)}：对键做hash，从$k$到0逐层比较阈值
$\text{s\_[i]} / \text{s\_[0]} \times 2^{32}$，返回第一个命中深度。

\subsection{last\_occupied\_idx\_优化}

\texttt{pop\_last\_occupied()}利用\texttt{last\_occupied\_idx\_}指针快速定位
最后一个占用槽。每次插入更新指针为$\max(\text{last\_idx}, \text{new\_slot})$，
删除时若恰好删除了最后一个槽则向后扫描更新。此优化将删除中tail→hole搬运
从$O(\text{capacity})$摊还为$O(1)$。

\section{Facility实现}

\subsection{两级路由查询}

\texttt{lookup(key)}：
\begin{enumerate}
  \item \texttt{cubby\_router\_.probe\_index(key)} → cubby索引$ci$
  \item $\text{cubbies\_}[ci].\texttt{lookup\_slot}(key)$ → 槽索引$slot$
  \item $\text{cubbies\_}[ci].\texttt{lookup\_at}(slot, key)$ → 返回值
\end{enumerate}

\subsection{合并与重建}

\texttt{merge\_two\_of\_tier(tier)}：提取两个候选Cubby的全部元素 →
\texttt{emplace\_back}新Cubby(容量更大) → 逐元素\texttt{insert\_new}重插入 →
擦除旧Cubby → 重建\texttt{cubby\_router\_}（O(N)，但合并稀疏）。

\chapter{LevelDB 集成}

本章描述将实现的哈希方案集成到Google LevelDB\cite{leveldb}数据库的MemTable中。

\section{集成动机}

LevelDB使用SkipList作为MemTable的底层存储结构，点查询（Get）的时间复杂度为
$O(\log n)$。将$O(1)$的k-kick哈希方案作为SkipList的点查询加速器，可提升读性能
的同时保留SkipList的有序迭代能力。

\section{适配层设计}

LevelDB的键是任意字节串（Slice），而Facility要求固定类型键值。适配层
\texttt{KickHashTable}完成类型转换：

\begin{itemize}
  \item \textbf{键转换}：Slice → \texttt{KickHash64()}（两次LevelDB Hash，不同种子，
    拼为64-bit哈希）→ \texttt{Facility<uint64\_t, uint64\_t>}的键
  \item \textbf{值转换}：Arena缓冲区指针 → \texttt{reinterpret\_cast<uint64\_t>}
    → Facility的值
  \item \textbf{查询验证}：从Facility取回Arena指针后，解析LevelDB编码的键值对，
    用原始Slice做最终键匹配，消除64-bit哈希碰撞可能
\end{itemize}

\section{MemTable修改}

\begin{itemize}
  \item \texttt{Add()}：在原有Arena编码 + SkipList::Insert之后，额外调用
    \texttt{kick\_table\_.Insert(key, buf\_ptr)}
  \item \texttt{Get()}：优先查询\texttt{kick\_table\_.Get(key)}，
    命中则解析Arena缓冲区返回值；未命中回退原有SkipList::Seek
  \item \texttt{NewIterator()}：不受影响，始终基于SkipList
\end{itemize}

\section{编译期开关}

通过CMake选项\texttt{USE\_KICK\_HASH}控制：

\begin{lstlisting}
# 启用 k-kick 哈希
cmake -B build -DUSE_KICK_HASH=ON
cmake --build build

# 使用原始 LevelDB
cmake -B build
cmake --build build
\end{lstlisting}

启用时，CMake添加\texttt{-DUSE\_KICK\_HASH=1}编译宏，并将
\texttt{-fexceptions}重新启用（Facility依赖异常处理）。

\section{注意事项}

\begin{itemize}
  \item \textbf{异常处理}：LevelDB默认禁用异常（\texttt{-fno-exceptions}），
    集成时需恢复异常支持
  \item \textbf{内存安全}：Arena在MemTable生命周期内不释放单个节点，
    Facility中存储的指针全程有效
  \item \textbf{多版本语义}：MemTable可包含同一键的多个版本（不同sequence number），
    Facility始终存储最新插入版本，与Get返回最新可见版本的语义一致
  \item \textbf{迭代器}：NewIterator始终基于SkipList，Facility作为哈希表不支持有序遍历
\end{itemize}

\chapter{总结与展望}

\section{工作总结}

本文完成以下工作：

\begin{enumerate}
  \item \textbf{算法复现}：基于Bender等人\cite{bender2022optimal}的$k$-kick树哈希
    理论，完整实现了MiniArray位压缩数组、LocalQueryRouter二叉Trie查询路由、Cubby
    弹性哈希表和Facility分层管理器四层组件，共计约1100行C++17模板代码。
  \item \textbf{踢出策略对齐}：实现了论文§3.1的优先级踢出机制（被踢键保持原深度）
    和\texttt{reserved}参数防数据丢失修复。
  \item \textbf{Trie查询路由}：根据论文§4.3重构LocalQueryRouter为二叉Trie最小唯一
    前缀结构（论文Lemma 15），实现Trie walk查询、split\_node分裂、cleanup\_leaf
    删除回溯，并以哈希指纹替代oracle进行键验证。
  \item \textbf{性能实验}：在$n\leq2^{20}$规模上与\texttt{std::unordered\_map}和
    \texttt{std::map}进行三操作全面对比。插入在$n=5\times10^5$处因合并触发全量路由
    重建出现134×跳变；查询3.11 s（Trie walk开销）；内存211 MB（对象式TrieNode
    32B/节点，对比论文紧凑编码 ∼2.5 B/key）。
  \item \textbf{数据库集成}：将方案集成为LevelDB MemTable的点查询加速器，
    提供\texttt{USE\_KICK\_HASH}编译期开关。
\end{enumerate}

\section{不足与展望}

\begin{itemize}
  \item \textbf{插入性能}：当前合并操作的全量路由重建（O(N)/次）是插入速度的主要
    瓶颈。论文§5.2 采用 per-cubby 独立路由架构，合并时无需全量重建。未来可重构为
    论文的多路由器架构以消除此 O(N) 开销。
  \item \textbf{紧凑编码}：当前 LocalQueryRouter 使用对象式 \texttt{vector<TrieNode>}
    （32B/节点），空间为论文紧凑编码 E$_1$+E$_2$ 的 ∼150×。实现紧凑比特编码
    是达到论文理论空间界 $O(\log^{(k)} n)$ bits/key 的关键。
  \item \textbf{路由器规模}：论文的每个 local query router 仅处理 O(log n / log log n)
    ≈ 93 个 key，当前全局路由器处理 1M 个 key（规模差 10$^4$×），导致 Trie 路径长
    度增长至 log$_2$(1M) ≈ 20 层。应采用论文的 per-cubby 多路由器分组架构。
  \item \textbf{动态容量}：当前容量体系为固定的4级（1024/41943/194932/716800），
    论文的容量参数 $K=\text{polylog} n$ 可随 $n$ 动态调整。
  \item \textbf{$k$参数化}：当前 $k$ 由 capacity 固定推导（约 4），论文的 $k$ 是用户
    可配置参数，可实现 $k=1,2,\ldots,\log^*n$ 的 tradeoff 曲线。
  \item \textbf{多线程}：当前实现为单线程，论文的 kick 树天然支持高并发踢出
    （不同 bin 互不干扰），可探索 lock-free 实现。
\end{itemize}
