\begin{abstract}
哈希表是支持动态数据操作的基础数据结构，其时空权衡一直是算法研究的核心议题。
2022年，Bender等人提出了一种基于$k$-kick树的新型哈希方案\cite{1}，
从理论上证明可通过将更新操作的时间复杂度放宽至$O(k)$，将每元素的空间浪费指数级
压缩至$O(\log^{(k)} n)$比特，打破了$\Omega(\log\log n)$的空间下界。
本文基于该理论实现了分层弹性哈希存储结构（Facility与Cubby），包含优先级踢出机制
（\S3.1）、基于MiniArray位压缩的紧凑二叉Trie局部查询路由（\S4.3 + Lemma 15）以及
8-bit Lookup Table查询加速\cite{7}。槽元数据和空闲槽位图分别通过双层MiniArray压缩至
每槽4比特和1比特，Trie节点以紧凑位编码存储（$\sim$5--8B/节点）。
在$n\leq 10^{6}$个32位键值对的实验规模下，与\texttt{std::unordered\_map}进行了
插入、查询、删除和空间占用的全面对比。实验表明：插入在$n\leq 2\times10^5$时
每操作仅$\sim$0.8 us（近似常数），合并策略避免了$O(N)$全量路由重建；
查询在LUT加速下达$\sim$1.95 us/op（$n=10^6$）；空间占用在$n=2\times10^5$时
仅9 MB（45 B/key），在$n=10^6$时为97 MB，通过动态cubby容量控制合并空间效率。
最后将方案集成为LevelDB MemTable\cite{2}的点查询加速器，提供编译期
（\texttt{-DUSE\_KICK\_HASH}）和运行时（\texttt{SetUseKickHash}）双向开关，
集成实验验证适配层开销仅5.17 ns/次，查询性能在$n=2\times10^5$时达0.35 us/op。

\noindent\textbf{关键词}：哈希表，时空权衡，k-kick树，位压缩路由，LevelDB
\end{abstract}

\begin{abstract*}
Hash tables are fundamental data structures supporting dynamic data operations,
with their time-space tradeoffs being a core topic in algorithm research.
In 2022, Bender et al.\ proposed a novel hashing scheme based on $k$-kick trees%
\cite{1}, theoretically proving that by relaxing update time to
$O(k)$, per-element space waste can be exponentially compressed to
$O(\log^{(k)} n)$ bits, breaking the $\Omega(\log\log n)$ lower bound.
This thesis implements the algorithm, constructing a hierarchical elastic hash
storage structure (Facility and Cubby), implementing the priority-based kicking
mechanism (\S3.1) and a compact binary trie local query router (\S4.3) using
MiniArray bit-packing (Lemma 15), with slot metadata compressed to 4+1 bits via
dual MiniArrays and an 8-bit lookup table\cite{7} for query acceleration.
Experiments with $n\leq 10^{6}$ 32-bit key-value pairs compare insertion, query,
deletion and space against \texttt{std::unordered\_map}.
The implementation achieves $\sim$0.8 us/op insertion for $n\leq 2\times10^5$
(near-constant) and avoids $O(N)$ full route-table rebuild through deactivate-based
merging. Query time is $\sim$1.95 us/op at $n=10^6$ with LUT acceleration.
Space is 9 MB at $n=2\times10^5$ (45 B/key) and 97 MB at $n=10^6$ (97 B/key),
controlled by dynamic cubby sizing.
The scheme is integrated into LevelDB's MemTable\cite{2} with a
\texttt{-DUSE\_KICK\_HASH} compile-time switch and \texttt{SetUseKickHash()} runtime
toggle. Integration benchmarks show adapter overhead of only 5.17 ns/op and
query performance of 0.35 us/op at $n=2\times10^5$.

\noindent\textbf{Keywords}: hash table, time-space tradeoff, k-kick tree, bit-packed routing, LevelDB
\end{abstract*}

\section{研究背景和意义}

哈希表是现代数据库管理系统、缓存系统和搜索引擎中最为基础的数据结构之一。
其核心目标是支持动态插入和删除操作，并保证查询的时间复杂度为$O(1)$，
即在理想状态下，查询、插入、删除的操作所需时间为常数级，不随存储数据量
$n$的增大而增加。为了实现这一点，哈希表往往需要在空间占用上做出让步，
通过额外的比特位存储信息来实现极低的时间复杂度。

在要求插入、删除及查询操作均维持恒定时间复杂度（即期望时间或最坏情况时间为
$O(1)$）的前提下，早期的理论工作\cite{3}表明，在严格限制更新操作
为$O(1)$时间且仅使用简单探测序列的模型下，每个键值对的空间冗余往往难以低于
$\Omega(\log \log n)$比特。这一理论下界长期制约着哈希表空间效率的进一步提升。

2022年，Bender等人发表的论文《关于哈希表最优时间/空间权衡》%
\cite{1}打破了这一僵局。这项研究提出了一种基于$k$-kick树
的新哈希方案，证明通过适当提高插入和删除操作的时间复杂度（从$O(1)$提高到
$O(k)$，其中$k$是一个人为指定的具有一定上限的常数），空间浪费可以以指数形式
降低至$O(\log^{(k)} n)$比特。这里$\log^{(k)} n$表示对$n$进行$k$次迭代对数
运算，即$\log^{(k)} n = \log(\log^{(k-1)} n)$，并定义$\log^{(0)} n = n$、
$\log^{(1)} n = \log n$。当$k = \log^{*} n$（等式右侧表示对$n$进行迭代求对数
直到结果小于等于1所需的次数，此时$\log^{(k)} n = O(1)$）时，空间浪费可以降低
到恒定的$O(1)$比特水平，实现了理论和工程上的重大突破。

本毕业设计旨在复现这一前沿的哈希算法，并将其集成到常见的数据库管理系统中。
研究意义如下：

\textbf{理论价值}：通过实验对论文理论进行验证，通过调整$k$的值研究$k$如何
影响时间与空间复杂度，探索最优的$k$值选择策略。

\textbf{工程价值}：减少内存使用意味着成本降低和并发能力增强，在内存有限
的场景中提高现有数据库的存储效率。将其集成到数据库观察空间存储效率提升
效果。

\section{研究现状}

哈希表作为支持几乎常数时间的插入、删除和查询操作的核心数据结构，其时间复杂度
和空间复杂度之间的权衡一直是现代算法的研究焦点。

\subsection{链式寻址法}

链式寻址法通过链表处理冲突和碰撞的问题，它在实现上相对简单并且支持动态扩容，
但每个节点都需要存储额外的指针开销，在查询时的探测深度也相当不平衡。链表节点
在内存中的非连续分布还会破坏缓存局部性，导致更高概率的缓存缺失。

\subsection{开放寻址法}

开放寻址法（如线性探测、二次探测）将所有元素存储于连续数组中，通过一个固定的
探测序列函数处理冲突。当当前元素哈希结果与已存入的元素冲突时，沿着探测序列
寻找下一个位置，直到不发生冲突。然而，随着负载因子$\alpha$趋近于1，冲突链
长度急剧增加，导致查询与插入因为要沿着长长的探测序列进行操作，时间复杂度退化。
因此其难以在保证$O(1)$时间复杂度的同时维持极高的空间利用率。

\subsection{Cuckoo Hashing}

Cuckoo Hashing由Pagh和Rodler于2001年提出\cite{4}，通过引入
多候选位置及元素重定位机制，在最坏情况下实现了$O(1)$的查询时间。多候选位置
改变了先前使用一个关于探测次数的探测函数生成探测序列的方式，转而采用多个哈希
函数为每个元素生成多个可存入位置，每一个元素只会出现在属于自己的可存入位置中。
元素重定位机制则从发现冲突退让并探测转变为发现可存入位置都有冲突就踢出一个
元素，将该元素往属于它的其他可存入位置移动，重复进行直到不再冲突。这两种机制
协作严格保证了任何键的查找操作只需要计算预先设置的哈希函数个数的次数，实现了
常数级查询。

\subsection{基于k-kick树的时空最优方案}

上述所有解决方案均未能突破前面提出的空间限制下界。而2022年发表的论文《关于
哈希表时间/空间权衡的最优方案》\cite{1}中提出的利用$k$-kick
树结构构建哈希表方案是目前最新的突破成果。该方案将哈希表映射问题转化为一个
层次化的``球到槽''问题，通过引入随机优先级和有限的不超过人为确定的$k$次元素
移动（即``$k$-kick''），从理论上证明，对于任何$k \geq 1$，都可以实现$O(k)$
时间复杂度的哈希表元素更新（插入、删除、查询）和$O(\log^{(k)} n)$比特的空间
浪费。

该研究还证明了此权衡曲线对于所有基于``增强开放寻址''框架的哈希表是紧确的
\cite{1}，即任何此类方案若更新时间为$t$，则每元素必须使用
$\Omega(\log^{(t)} n)$位的冗余。这意味着，若要在次对数级的更新时间下实现
$O(1)$位的空间冗余，必须彻底脱离``增强开放寻址''的范式。

\section{主要研究内容和目标}

本选题旨在复现并验证2022年提出的基于$k$-kick树的最优时空权衡哈希算法，
并探索其在数据库存储中的实际应用潜力。具体研究内容包括以下四个目标：

\begin{enumerate}
  \item \textbf{数据结构的实现和算法复现}：依照论文\cite{1}中的定义，构建基于$k$-kick树
    的分层存储结构，并实现从根节点到叶节点的动态元素分配逻辑。实现高效的kick
    策略，模拟论文中的随机优先级机制，建立在插入冲突时通过$k$次元素移动将
    新元素安置或触发上层重组并完成的机制，保证$O(k)$的时间复杂度。实现紧凑
    的辅助路由结构，用于快速定位元素所在的探测层级。

  \item \textbf{数据库存储集成与适配}：设计形式化的哈希表操作接口，对外只暴露
    insert、delete、get等操作，屏蔽底层逻辑设计提高兼容性。

  \item \textbf{理论正确性验证与复杂度分析}：基于代码实现，形式化验证算法
    复杂度，结合理论推导与实验数据，量化分析参数$k$对更新时间$T(n)$和空间
    浪费$S(n)$的具体影响，验证$S(n) = O(\log^{(k)} n)$的正确性。

  \item \textbf{性能对比实验}：构建包含标准库中的\texttt{std::unordered\_map}作为
    对照组，在相同硬件环境下进行全方位性能比对。测试不同数据规模下插入、查询、
    删除操作的时间开销和空间占用情况。
\end{enumerate}

\chapter{相关理论基础}

\section{哈希表基本概念}

哈希表（Hash Table）是一种通过哈希函数将键（key）映射到表中位置（slot）
来实现快速数据存取的数据结构。一个标准的哈希表支持三种基本操作：

\begin{itemize}
  \item \textbf{插入}（Insert）：将键值对$(k, v)$存入表中
  \item \textbf{查询}（Query/Lookup）：给定键$k$，返回对应的值$v$
  \item \textbf{删除}（Delete）：给定键$k$，从表中移除对应记录
\end{itemize}

理想情况下，三种操作均可在$O(1)$时间内完成。然而，当两个不同的键被哈希函数
映射到同一位置时，就会发生\textbf{冲突}（collision）。冲突处理策略是哈希表设计
的核心难题，不同的策略直接决定了哈希表在时间效率和空间占用上的表现。

\subsection{哈希函数}

哈希函数$h: U \rightarrow [m]$将键从全域$U$映射到$m$个槽中。一个好的哈希函数
应满足：
\begin{itemize}
  \item \textbf{确定性}：同一键总是映射到同一位置
  \item \textbf{均匀性}：每个槽被映射到的概率近似相等
  \item \textbf{高效性}：计算速度快，$O(1)$时间
\end{itemize}

本文使用\texttt{splitmix64}\cite{5}作为最终化函数，对不同的
使用场景通过不同种子值（seed）生成独立哈希族\cite{6}。

\subsection{负载因子与空间效率}

负载因子（load factor）$\alpha = n/m$表示当前存储元素数$n$与总槽数$m$的比值。
空间效率通常用\textbf{每键浪费比特数}（wasted bits per key）$r$来衡量：
若信息论最优空间为$\mathcal{B}$比特，哈希表使用$\mathcal{B} + rn$比特，则称
浪费了$r$比特/键。本文研究的核心问题是如何在保障时间效率的前提下最小化$r$。

\section{Cuckoo Hashing}

Cuckoo Hashing\cite{4}是一种经典的开地址哈希方案，其核心思想
是每个键有$d$个候选位置（通常$d=2$），由$d$个独立哈希函数分别确定。
当插入新键时：
\begin{enumerate}
  \item 依次检查$d$个候选位置，找到第一个空位即插入
  \item 若所有候选位置均被占用，随机选择一个候选位置上的现有键``踢出''（kick out），
    新键占据该位置
  \item 被踢出的键尝试在其\textbf{其他}候选位置中寻找空位
  \item 重复上述过程，直到所有键都找到位置或达到预设的最大踢出次数
\end{enumerate}

Cuckoo Hashing的优势在于\textbf{查询严格为$O(1)$}（只需检查$d$个位置），
但其负载因子通常受限（$d=2$时约$50\%$）。

\section{k-kick树哈希方案}

Bender等人\cite{1}提出的$k$-kick树方案是对Cuckoo思路的重大
推广。其核心创新在于：

\subsection{多层级bin划分}

将哈希表的$m$个槽组织为$k+1$个层级（depth $0,1,\ldots,k$）的bin层次结构。
Depth-0的bin包含全部$m$个槽，depth-$i$（$i>0$）的bin大小为
$s_i = \Theta((\log^{(i)} m)^6)$。随着深度增加，bin大小呈指数级递减。
这种层次结构被称为\textbf{$k$-kick树}。

\subsection{优先级踢出策略}

每个键$x$被随机分配一个最大深度$s(x)$，满足\cite{1}
$\Pr[s(x) < i] = 1/(\log^{(i)} n)^2$。插入时按以下规则操作：

\begin{enumerate}
  \item 新键$x$试图在尽可能深的bin中寻找空位
  \item 若目标bin无空位且\textbf{未饱和}（存在深度较低的键）：
    踢出该低深度键，新键占据其位置
  \item 被踢键\textbf{保持原深度不变}，在其自身深度bin中寻找新空位
  \item 被踢键若触发新一轮踢出，则形成\textbf{踢出链}，但总踢出次数不超过$k$
\end{enumerate}

\textbf{关键性质}：高深度（小bin）的键优先踢出低深度（大bin）的键，被踢键
保持原深度。每次插入至多触发$k$次踢出，因此\textbf{切换开销}为$O(k)$。

\subsection{理论保证}

论文\cite{1}证明，对于任意$k \in [\log^* n]$，上述方案可实现：
\begin{itemize}
  \item 插入/删除时间：$O(k)$（高概率）
  \item 查询时间：$O(1)$（确定性）
  \item 每键空间浪费：$O(\log^{(k)} n)$比特（高概率）
\end{itemize}

此结果打破了长期存在的$\Omega(\log\log n)$空间下界，展示了时空权衡的极致
曲线：每次增加常数的更新时间，空间浪费可\textbf{指数级减少}。

\section{MiniArray：位压缩数组}

\subsection{设计动机}

在紧凑哈希表中，大量元数据（槽状态、路由条目）的位宽远小于标准整型（64 bits）。
例如槽元数据仅需4比特（occupied + depth），路由条目中cubby索引仅需11比特。
若使用\texttt{std::vector<uint64\_t>}存储，每个元素固定64比特，造成严重空间浪费。

MiniArray通过将元素紧密平铺在连续位流中，实现了\textbf{精确位宽存储}\cite{1}。

\subsection{双模存储}

\begin{figure}[H]
\centering

\section{LocalQueryRouter：紧凑二叉Trie局部查询路由}

\subsection{设计原理（论文 \S4.3 + Lemma 15）}

论文\cite{1}的局部查询路由器将每个键$x$哈希为64-bit全随机二元串$r_x$，在集合$S$上构建
\textbf{最小唯一前缀二叉Trie} $T$：对每个$r_x$，取最短的、不与任何其他$r_y$冲突
的前缀作为该键的唯一标识。Trie 的叶节点存储该键对应的 probe 值 $f(x)$。

论文 Lemma 15 证明：随机二元串的 Trie 期望规模为 $O(k)$ 个节点（其中 $k=|S|$），
且对任意常数 $c>1$，存在 $\varepsilon>0$ 使得 $|T|\leq (\log n)/c$ 以高概率成立。

\subsection{紧凑节点编码}

本次实现将 Trie 及 f-values 以紧凑位编码存储于 MiniArray 中：

\begin{itemize}
  \item \textbf{节点编码}：每个节点固定 $w=\texttt{entry\_bits\_}$ 位宽，
    最高位为类型标志（0=内部节点, 1=叶节点）。
    内部节点存储 left\_child + right\_child 两个显式子指针（各 $\texttt{child\_bits\_}$ 位），
    叶节点存储 f\_value（$\texttt{fval\_bits\_}$ 位）+ 键哈希指纹（$\texttt{kh\_bits\_}$ 位，
    默认44位）。
  \item \textbf{查询}（\texttt{walk\_down}）：沿键的 LSB 方向哈希位遍历 Trie，
    遇叶节点用指纹验证后返回 f\_value。
  \item \textbf{插入}（\texttt{insert + do\_split}）：沿路径 walk → 遇异键叶时分裂
    （找两键哈希分叉位 → 创建内部节点链 → 两新叶）→ 遇 NO\_CHILD 空方向时链接新叶。
  \item \textbf{删除}（\texttt{remove}）：walk\_down 找到叶 → 标记为空叶（hash=0, fval=0）。
\end{itemize}
整体空间 $= |\texttt{nodes\_}| \times w$ bits，其中 $|\texttt{nodes\_}| \approx 2|S|$，
$w \le 62$ bits。紧凑编码实现了每节点 $\sim$5-8 bytes 的空间占用。

\subsection{Lookup Table 加速}

论文提出通过 Method of Four Russians\cite{7} 式的
lookup table 将 Trie 遍历从 $O(\log|S|)$ 加速至 $O(1)$。
本实现采用简化版 8-bit LUT：预计算哈希低 8 位的全部 256 种可能路径在 Trie 中
的目标节点，查询时直接跳转至该节点后继续遍历剩余位数。
LUT 在 Trie 结构变化时失效（仅当 \texttt{nodes\_.size()} 增长时），
叶值更新不影响 LUT 有效性。LUT 存储开销为 $256 \times 4\text{B} = 1\text{KB}$。

\section{Cubby：单级弹性哈希表}

Cubby是$k$-kick树的载体\cite{1}。每个Cubby有容量$m$（支持动态指定，构造时可传入
\texttt{desired\_capacity}参数）和$k+1$个深度层级。

\subsection{槽元数据编码}

每槽使用4比特位压缩存储：
\begin{itemize}
  \item bit 0: occupied（1=已占用）
  \item bit 1--3: depth（0--7，该槽所在kick深度）
\end{itemize}

另设1比特 \texttt{free\_bitmap\_} 标识空闲槽（1=空闲），配合
\texttt{first\_free\_} 缓存指针实现近似$O(1)$的空闲槽查找。

\subsection{踢出算法}

Cubby的核心算法\texttt{try\_place}实现了论文\S3.1\cite{1}的优先级踢出：

\begin{algorithm}[H]
\caption{try\_place(key, max\_depth)}
\begin{algorithmic}[1]
\FOR{$d = max\_depth$ down to $0$}
  \STATE $bin \gets bin\_for\_key(key, d)$
  \STATE Phase 1: 扫描$bin$，若找到空槽则返回
  \IF{$d > 0$}
    \STATE Phase 2: 扫描$bin$中深度$< d$的占槽
    \IF{找到}
      \STATE 暂存$victim\_key, victim\_val$
      \STATE 清空该槽
      \STATE 递归\texttt{try\_place}(victim, victim\_depth, kick\_idx)
      \IF{成功}
        \STATE victim移入新槽，新键占据该槽
        \RETURN
      \ELSE
        \STATE 恢复原槽
      \ENDIF
    \ENDIF
  \ENDIF
\ENDFOR
\RETURN FAIL
\end{algorithmic}
\end{algorithm}

被踢键\textbf{保持原深度}，在其自身深度bin中寻找新空位。算法中的\texttt{reserved}
参数防止被踢键在递归扫描时``发现''刚被清空的原槽。

\section{LocalQueryRouter实现（紧凑MiniArray Trie + LUT）}

\subsection{紧凑节点编码}

\begin{figure}[H]
\centering
\begin{verbatim}
每节点固定 entry_bits_ 位，MiniArray Uniform 模式存储：
  ┌──────┬────────────────────────────────────────────────────┐
  │1 bit │             entry_bits_ - 1  bits                   │
  ├──────┼────────────────────────────────────────────────────┤
  │ type │                 数据字段                            │
  └──────┴────────────────────────────────────────────────────┘

内部节点: type=0, 数据=[left_child(高位)][right_child(低位)]
叶节点:   type=1, 数据=[f_value(高位)][key_hash(低位)]
          key_hash = splitmix64(hash(key)) & ((1<<44)-1)
  child_bits_ = bits_to_represent(cap*3 + NODE_PAD)
  fval_bits_  = 由使用场景决定
  kh_bits_    = 44 (默认)
  entry_bits_ = 1 + max(2*child_bits_, fval_bits_+kh_bits_) ≤ 62
\end{verbatim}
\caption{紧凑节点编码方案}
\label{fig:compact_node}
\end{figure}

\subsection{核心算法}

\textbf{查询 (probe\_index)}：对 key 计算哈希得到 64-bit 二元串，
从根节点沿 LSB 位遍历 Trie。若 LUT 有效则跳过前 8 层直接跳转至目标节点。
遇叶节点用指纹验证：匹配则返回 f\_value，否则返回 SIZE\_MAX。

\textbf{插入 (insert)}：沿 key 的 LSB 哈希位遍历 Trie。五种情况：
\begin{enumerate}
  \item 遇叶节点且指纹匹配 → 更新 f\_value
  \item 遇叶节点且指纹为0（空叶，首次使用）→ 覆盖为新键数据
  \item 遇叶节点但指纹不匹配 → \texttt{do\_split()} 分裂：
    找分叉深度 → 创建内部节点链 → 在分叉处创建两新叶
  \item 遇内部节点但方向为 NO\_CHILD → 创建新叶并链接
  \item 路径走到头 → 追加新叶节点
\end{enumerate}
插入结束后若 \texttt{nodes\_.size()} 变化则失效 LUT。

\textbf{do\_split(leaf\_idx, depth, e\_hash, e\_fval, n\_hash, n\_fval)}：
\begin{enumerate}
  \item 从 depth 起找两 hash 的首个分叉位 diverge
  \item 从 depth 到 diverge-1 逐位创建内部节点链（每次 alloc\_node）
  \item 若当前节点为原叶：转换为 internal；若为内部节点：更新对应方向子指针
  \item 在 diverge 处创建 e\_leaf（已存键）和 n\_leaf（新键）
  \item 设置最后一个内部节点的左右子节点为两叶
\end{enumerate}

\textbf{删除 (remove)}：沿 Trie walk 找到匹配叶节点 → 写入空叶标记
（fval=0, hash=0），n\_entries\_--。

\subsection{显式双指针与LUT}

采用显式 left+right 双指针设计，Split 时新节点通过 \texttt{alloc\_node()} 在数组
末尾分配，确保已有节点的子指针关系不被破坏。LUT 通过 \texttt{ensure\_lut()} 方法
构建，在前 8 位共 256 种路径中预计算目标节点。

\section{Cubby实现}

\subsection{bin参数计算}

\texttt{compute\_kick\_params()}：从\texttt{capacity\_}出发迭代
$\lceil\log_2(x+1)\rceil$得到$k$（$\le 4$），对每层应用迭代对数压缩后平方取整
得到\texttt{s\_[i]}。初始化\texttt{free\_count\_[d]}为各深度的总槽数。

\subsection{深度分配}

\texttt{max\_depth\_for(key)}：对键做hash，使用概率公式
$\Pr[s(x) < i] = 1/(\log^{(i)} n)^2$ 计算阈值，从$k$到0逐层比较并返回第一个命中深度\cite{1}。

\subsection{空闲槽查找}

\texttt{free\_bitmap\_}（MiniArray, 1 bit/slot, 0=占用, 1=空闲）配合
\texttt{first\_free\_}缓存指针，实现近似 O(1) 的空闲槽查找。
\texttt{find\_free\_in\_bin()} 从缓存的 \texttt{first\_free\_} 位置起扫描目标 bin，
插入后清 bit，删除后置 bit 并更新缓存。

\section{Facility实现}

\subsection{两级路由查询}

\texttt{lookup(key)}：
\begin{enumerate}
  \item \texttt{cubby\_router\_.probe\_index(key)} → cubby索引$ci$
  \item $\text{cubbies\_}[ci].\texttt{lookup\_slot}(key)$ → 槽索引$slot$
  \item $\text{cubbies\_}[ci].\texttt{lookup\_at}(slot, key)$ → 返回值
\end{enumerate}

\subsection{合并与路由更新}

\texttt{merge\_two\_of\_tier(tier)}：选取两个候选Cubby → 提取全部元素 →
按实际数据量计算动态容量 → \texttt{alloc\_cubby\_slot}获得新Cubby →
逐元素插入新Cubby并逐一更新\texttt{cubby\_router\_}中键到cubby索引的映射
→ \texttt{deactivate()}原Cubby。使用\texttt{deactivate()}停用避免
\texttt{vector::erase}带来的索引偏移。

相比unordered\_map慢约15--25×，主要差距来自紧凑Trie的逐位遍历和两级路由开销
（facility级+cubby级），vs 哈希表单次探测。LUT加速\cite{7}将查询前8层从逐位遍历
优化为$O(1)$跳转，查询时间在$n\leq 10^5$时已达每操作$<0.3$ us，$n=10^6$时约1.95 us/op。

\chapter{LevelDB 集成}

本章描述将实现的k-kick树哈希方案集成到Google LevelDB\cite{2}数据库的MemTable中，
包括集成流程、适配层设计、双向开关机制，并通过实验验证集成效果。

\section{集成动机}

LevelDB\cite{2}的MemTable使用SkipList作为底层存储结构。SkipList支持
$O(\log n)$的点查询（Get）、有序遍历和范围扫描，但在高读写混合负载下，
SkipList的逐节点比较和指针追逐会带来较高的缓存缺失和延迟。

k-kick哈希方案通过紧凑二叉Trie路由实现了$O(1)$期望点查询\cite{1}，
将其作为MemTable的\textbf{点查询加速器}可以在保留SkipList有序迭代能力
的前提下加速Get操作。用户在写入时双写SkipList和KickHashTable，查询时
优先走KickHashTable的$O(1)$路径，命中则直接返回，未命中或哈希碰撞时
回退至SkipList的$O(\log n)$路径。

\section{集成流程}

整体集成分为以下四个步骤：

\begin{enumerate}
  \item \textbf{代码复制}：将\texttt{./code}目录中最新版本的四个头文件
    （\texttt{facility.hpp}、\texttt{cubby.hpp}、\texttt{miniarray.hpp}、
    \texttt{local\_query\_router.hpp}）复制至\texttt{leveldb/util/kick\_hash/}
    目录，包含free\_bitmap\_空闲槽追踪、deactivate停用合并、动态容量分配、
    8-bit Lookup Table加速等全部优化。
  \item \textbf{适配层编写}：在\texttt{util/kick\_hash.h}中实现
    \texttt{KickHash64}哈希函数和\texttt{KickHashTable}包装器类，
    完成Slice键到Facility模板参数的映射转换。
  \item \textbf{MemTable修改}：在\texttt{db/memtable.h}和\texttt{db/memtable.cc}中，
    添加条件编译分支\texttt{\#ifdef USE\_KICK\_HASH}，在Add和Get中插入KickHashTable
    的读写逻辑，同时新增运行时开关\texttt{use\_kick\_hash\_}。
  \item \textbf{构建集成}：修改\texttt{CMakeLists.txt}，新增\texttt{USE\_KICK\_HASH}
    选项（默认OFF），启用时传递\texttt{-DUSE\_KICK\_HASH=1}编译宏并恢复异常支持
    （\texttt{-fexceptions}）。
\end{enumerate}

\section{适配器设计}

\subsection{KickHash64哈希函数}

适配器首先需要将LevelDB的任意字节串键（Slice）映射为64-bit哈希值，
以适配Facility的\texttt{uint64\_t}键类型。

\begin{itemize}
  \item 调用两次LevelDB内置\texttt{Hash()}函数（种子分别为
    \texttt{0xbc9f1d34}和\texttt{0x5c6b7a8e}），各得到32-bit哈希值
  \item 将两值拼接为64-bit哈希：$\text{KickHash64}(d,n) = (H_2 \ll 32) \;|\; H_1$
  \item 参考Belazzougui等人\cite{6}的多哈希族构造方法，两独立种子确保哈希均匀性
\end{itemize}

值映射 & Arena指针 $\xrightarrow{\text{reinterpret\_cast}}$ uint64\_t \\
存储引擎 & Facility<uint64\_t, uint64\_t>（两级LUT路由） \\

\subsection{KickHashTable包装器}

\texttt{KickHashTable}类封装了Facility对象，提供三个与MemTable匹配的操作接口：

\begin{lstlisting}
class KickHashTable {
 public:
  void Insert(const Slice& user_key, uint64_t arena_ptr) {
    table_.insert(KickHash64(key, len), arena_ptr);
  }
  bool Get(const Slice& user_key, uint64_t* out) {
    return table_.lookup_value(KickHash64(key, len), *out);
  }
  void Remove(const Slice& user_key) {
    table_.remove(KickHash64(key, len));
  }
 private:
  Facility<uint64_t, uint64_t> table_;
};
\end{lstlisting}

Facility的\texttt{lookup\_value}支持非异常返回（通过bool返回值），
避免了LevelDB禁用异常的兼容问题。插入和删除通过\texttt{insert}和\texttt{remove}完成，
Facility内部自动处理踢出链、合并和路由更新。

\section{MemTable集成改动}

\subsection{数据结构扩展}

在\texttt{MemTable}类中增加条件编译成员：

\begin{lstlisting}
class MemTable {
  // ... 原有成员 ...
  Table table_;                    // SkipList（保留，用于迭代）

#ifdef USE_KICK_HASH
  KickHashTable kick_table_;       // k-kick 哈希加速器
  bool use_kick_hash_;             // 运行时开关
#endif
};
\end{lstlisting}

\subsection{写入路径（Add）}

\begin{lstlisting}
void MemTable::Add(seq, type, key, value) {
  // 原有: Arena 编码 → SkipList::Insert
  char* buf = arena_.Allocate(encoded_len);
  // ... 编码 key/value/tag ...
  table_.Insert(buf);

#ifdef USE_KICK_HASH
  if (use_kick_hash_) {
    kick_table_.Insert(key,
        reinterpret_cast<uint64_t>(buf));
  }
#endif
}
\end{lstlisting}

\begin{enumerate}
  \item Arena缓冲区的原始指针作为\texttt{uint64\_t}值存入Facility
  \item Arena在MemTable生命周期内不释放单个节点，指针全程有效
  \item 运行时开关\texttt{use\_kick\_hash\_}控制是否启用双写
\end{enumerate}

\subsection{查询路径（Get）}

\begin{lstlisting}
bool MemTable::Get(const LookupKey& key, ...) {
#ifdef USE_KICK_HASH
  if (use_kick_hash_) {
    uint64_t arena_ptr;
    if (kick_table_.Get(key.user_key(), &arena_ptr)) {
      const char* entry = (const char*)arena_ptr;
      // 解析: varint32+internal_key+tag+varint32+value
      uint32_t key_len;
      const char* kp = GetVarint32Ptr(entry, entry+5, &key_len);
      if (user_key_match(kp, key)) {
        // 提取value（处理kTypeValue/kTypeDeletion）
        return true;
      }
      // 哈希碰撞 → 回退SkipList
    }
  }
#endif
  // 原有: SkipList::Seek → 解析
}
\end{lstlisting}

\begin{itemize}
  \item 优先通过两级路由（facility级$\rightarrow$cubby级）定位槽，
    从Facility取回Arena指针
  \item 从Arena缓冲区解析LevelDB编码的键值对
  \item 用原始Slice比对验证，防止64-bit哈希碰撞（概率$\sim 10^{-7}$）
  \item 碰撞或指针失效时自动回退至SkipList查找
\end{itemize}

\subsection{运行时开关：MemTable::SetUseKickHash()}

在\texttt{USE\_KICK\_HASH=ON}编译后，MemTable提供公开的运行时控制接口：

\begin{lstlisting}
// 运行时启用 k-kick 哈希加速（默认true）
memtable->SetUseKickHash(true);

// 运行时禁用，回退纯SkipList
memtable->SetUseKickHash(false);

// 查询当前状态
bool enabled = memtable->GetUseKickHash();
\end{lstlisting}

运行时开关在不变更二进制的前提下，允许\textbf{同一进程内不同的MemTable实例采用不同策略}，
或对同一实例在运行时动态切换。这使A/B对比测试无需重新编译，只需在一个测试中先后
（或并行对比）测试两种路径。

\section{集成总结}

本章完成了将k-kick树哈希方案集成到LevelDB MemTable中的完整工作：

\begin{enumerate}
  \item \textbf{代码移植}：将\texttt{./code}中最新的四个头文件（含free\_bitmap、
    deactivate合并、动态容量、LUT加速等全部优化）复制至\texttt{./leveldb/util/kick\_hash/}，
    保持了与原始实现的完全一致。
  \item \textbf{适配器设计}：\texttt{KickHashTable}包装器通过
    Slice→KickHash64→Facility<uint64\_t, uint64\_t>的转换链，
    将LevelDB的任意字节串键映射为Facility的固定类型键。碰撞保护通过取回Arena指针后
    的原始Slice比对实现。
  \item \textbf{MemTable双路径}：在Add中同时写入SkipList和KickHashTable，
    在Get中优先查询KickHashTable（$O(1)$），失败时回退至SkipList（$O(\log n)$）。
    NewIterator不受影响，始终基于SkipList。
  \item \textbf{双向开关}：编译期开关（CMake \texttt{USE\_KICK\_HASH}）控制代码编译和异常支持；
    运行时开关（\texttt{SetUseKickHash(bool)}）允许同一二进制内动态选择方案，
    无需重新编译即可进行A/B对比测试。
  \item \textbf{实验验证}：在$n \le 10^6$规模上与\texttt{std::unordered\_map}对比显示，
    适配层开销仅$\sim$5.17 ns/次，查询$\sim$0.35 us/op（$n=200$K，LUT加速），
    插入$\sim$0.86 us/op（近似$O(k)$），正确率100\%无碰撞误判。
\end{enumerate}

\chapter{总结与展望}

\section{工作总结}

本文完成以下工作：

\begin{enumerate}
  \item \textbf{算法实现}：基于Bender等人\cite{1}的$k$-kick树哈希
    理论，实现了MiniArray位压缩数组、LocalQueryRouter紧凑二叉Trie查询路由
    （含8-bit Lookup Table加速\cite{7}）、
    Cubby弹性哈希表（含free\_bitmap\_空闲槽追踪和动态容量）
    和Facility分层管理器（含deactivate-based合并和动态cubby sizing）四层组件，
    共计约1065行C++20模板代码。
  \item \textbf{踢出策略对齐}：完整实现了论文\S3.1\cite{1}的优先级踢出机制（被踢键保持原深度）
    和\texttt{reserved}参数防数据丢失修复，踢出链通过KickList层层向上传递。
  \item \textbf{紧凑Trie查询路由}：LocalQueryRouter基于MiniArray位编码的紧凑
    二叉Trie（显式left+right双指针、LSB哈希导航），实现walk\_down查询、do\_split分裂、
    空叶标记删除，以44-bit哈希指纹进行键验证。增加8-bit Lookup Table（256项）将查询
    前8层从逐位遍历加速为$O(1)$跳转\cite{7}。
  \item \textbf{性能实验}：在$n\leq10^6$规模上与\texttt{std::unordered\_map}进行三操作
    全面对比。$n=2\times10^5$时插入0.16 s（0.8 us/op），内存9 MB（45 B/key）；
    deactivate合并策略将合并复杂度控制在$O(\text{merged\_keys})$；
    $n=10^6$时内存97 MB（动态容量控制），查询1.95 us/op（LUT加速）。
    主要不足为大$n$下合并摊还导致插入升至9.5 us/op。
  \item \textbf{数据库集成}：将方案集成为LevelDB MemTable\cite{2}的点查询加速器，
    提供编译期（CMake \texttt{USE\_KICK\_HASH}）和运行时（\texttt{SetUseKickHash}）
    双向开关，适配层开销仅5.17 ns/次。集成实验在$n=10^6$规模上验证了正确性
    （全部查询命中率100\%）和查询加速（$n=2\times10^5$时0.35 us/op）。
\end{enumerate}

\section{不足与展望}

\begin{itemize}
  \item \textbf{Per-cubby独立路由}：当前仍使用全局cubby\_router\_（紧凑但全局）。
    论文\cite{1}的per-cubby多路由器分组架构（每路由器仅处理$O(\log n/\log\log n)\approx 93$键）
    可实现真正独立的路由更新，每次合并无需遍历全量键，从而降低大$n$下的插入摊还开销。
  \item \textbf{完全动态容量}：当前动态容量使用$\max(\text{公式}, \text{merged\_size}\times 2)$
    的启发式策略。论文\cite{1}的完整动态容量体系$C_j=K/(\log^{(j)}n)^2$中$K$应随总元素数$n$
    动态调整，实现更精确的cubby sizing以进一步提升空间利用率。
  \item \textbf{$k$参数化}：当前$k$由capacity固定推导（约4），论文\cite{1}的$k$是用户
    可配置参数，可实现$k=1,2,\ldots,\log^*n$的tradeoff曲线。
  \item \textbf{多线程}：当前实现为单线程，论文\cite{1}的kick树天然支持高并发踢出
    （不同bin互不干扰），可探索lock-free实现。
  \item \textbf{更高效的LUT}：当前LUT为8-bit（256项），完整Method of Four Russians\cite{7}
    实现可进一步扩大LUT位宽或以分段方式处理，将查询从$O(\log |S|)$完全降至$O(1)$。
\end{itemize}
